Core write operations (recording a purchase was the reproduction case) can hang indefinitely — no error, no timeout, no feedback — under ordinary concurrent load, because the database connection pool is capped at 3 connections. A single busy shop screen alone opens 6–8 parallel API calls. This must be fixed and load-tested before go-live. Two further defects (a raw unresolved-code placeholder, and a crashing search-box translation call) are real but lower-stakes. See the Critical/High section below for reproduction evidence.

Bug Summary

5 defects
BUG-001CriticalInfrastructure / Purchases · Billing (shared)
Purchase save hangs indefinitely under connection-pool contention — no timeout, no error

Where: Purchases → Record Purchase Invoice (Udyog/Wholesaler), and by code path the same risk applies to every route using an interactive Prisma transaction — Billing checkout included.

Repro: Filled a real purchase invoice (supplier, warehouse, 3 units of a variant product, ₹1,800 total) and pressed Record Purchase twice, in two separate attempts on a freshly restarted server. Both times the button spun with zero feedback for over two minutes; the server access log never printed a completion line for the request at all.

Root cause (confirmed in server logs):

[API] Error fetching purchases: PrismaClientKnownRequestError Invalid `prisma.purchaseInvoice.findMany()` invocation: Timed out fetching a new connection from the connection pool. (Current connection pool timeout: 30, connection limit: 3)

Why it matters: connection_limit=3 is set on the database URL. A single dashboard page load in this app already fires 6–8 concurrent API calls (products, godowns, master-data, suppliers, calendar, notifications, shop/profile …) — three connections is not enough for one active tab, let alone a shop with two staff billing at the counter simultaneously. Once the pool is exhausted, writes don't fail fast — they hang forever with a spinner, which reads to a shopkeeper as "the app is frozen," with no way to know if the sale/purchase actually saved.

Verified: both hung attempts were confirmed to have not committed (checked directly against the database — no purchase record was created either time).

Fix direction: raise the connection pool limit to something sized for real concurrent traffic (check the actual Supabase plan's connection ceiling first), and separately, every write path needs a hard client-side and server-side timeout with a visible retry/error state — a spinner with no upper bound is never acceptable on a money-moving action.

BUG-002HighPurchases — Add Supplier inline
Unresolved translation expression rendered as literal text in the supplier-name field

Where: Purchases → New Purchase → Supplier field → "+" (add supplier inline).

Repro: Click "+" next to the Supplier dropdown. The input's placeholder shows, verbatim, on screen:

{t('enterSupplierName') || 'Enter supplier name...'}

instead of the intended placeholder text. The field still functions — typing and saving a supplier name works — but every shopkeeper who opens this modal sees raw code.

Fix direction: the placeholder prop is almost certainly being passed as a literal string rather than an evaluated template expression — find the JSX and make sure the t(...) call is inside {'{'}...{'}'}, not inside quotes.

BUG-003MediumGlobal — top search bar
GlobalSearch placeholder throws a server-side i18n error on render

Where: components/GlobalSearch.tsx:80, logged live during this pass.

Error: INVALID_MESSAGE: Incorrect locale information provided (undefined) at GlobalSearch (components/GlobalSearch.tsx:80:29) const searchPlaceholder = t('searchPlaceholder', { type: searchTargetLabel });

The app recovered and kept serving pages, so this is not a hard crash for the user, but a component throwing on every render it hits is a real defect and worth root-causing — searchTargetLabel (itself from t('parties') / t('customers')) is coming back in a shape the ICU interpolation for searchPlaceholder doesn't accept.

BUG-004MediumBilling — GST invoices
Some GST sales are missing the itemized tax breakdown (gstDetails)

Where: checked a real, already-completed GST sale in the database (billType: "gst", gstAmount: ₹90) — its gstDetails field (meant to hold the CGST/SGST rate-group breakdown used by GST reports) was null.

The total tax amount is still correct and charged, so billing itself isn't broken — but a report relying on gstDetails for a CGST/SGST split on this invoice would show nothing. Worth confirming whether this is a specific billing path that skips writing it, or historical data from before the field existed.

BUG-005LowPurchases — line-item cost input
Typing into a cost field pre-filled with "0" prepends instead of replacing

Clicking the Unit Cost box (defaults to 0) and typing 600 produces 0600 rather than 600 — cosmetic only, it still parses to the correct number and the line total calculated correctly (₹1,800 for 3 × ₹600). A number field should select-all or clear on focus so the visible value never looks wrong even briefly.
